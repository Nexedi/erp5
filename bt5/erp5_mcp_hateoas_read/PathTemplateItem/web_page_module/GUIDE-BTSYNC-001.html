Sync Business Templates between the instance and their git working copies

Every BT here has a canonical git working copy. Two repos matter: /srv/slapgrid/slappart49/srv/project/woelfel-dev/woelfel-erp5 (branch master, upstream klaus/master) holds the woelfel_* BTs; /srv/slapgrid/slappart49/srv/project/woelfel-dev/erp5 (branch mcp, upstream klaus/mcp) holds erp5_mcp* and other framework BTs.

The four repository tools

  • erp5_bt_status(business_template=...) — read-only 3-way comparison: baseline (git HEAD), repository files, installed ERP5. Scope it with path_pattern (e.g. '*supply_line*') and/or summary_only/max_list — a scoped status on a 1000+-file BT (woelfel_core) answers in seconds what a full sweep gave up on with timeouts. On a full status timing out, work from git status plus a scoped erp5_bt_commit(dry_run).
  • erp5_bt_update_from_repository(business_template=...) — repository → ERP5. Refuses both-side conflicts unless force=true; runs a component-validation gate over the .py sources it will apply (broken code never installs).
  • erp5_bt_export_to_repository(business_template=..., changelog=...) — ERP5 → repository, then commits the whole BT (one changelog, only this BT's paths; unrelated working-copy dirt is never touched). dry_run=true previews. Needs a built BT doc: export() does not build — call bt.build() first (erp5_bt_commit's extractBT does it for you).
  • erp5_bt_install_from_repository(business_template=...) — only for BTs not yet installed; refuses with already_installed otherwise.

The preferred developer loop (no inline code payloads)

  1. Edit the .py/.xml files in the BT directory with ordinary file tools (read/edit/write, git diff for review).
  2. erp5_bt_update_from_repository installs the files into the instance.
  3. Test (erp5_live_test, verdict-only output).
  4. Commit and push with plain git in the working copy.

Scoping commits in a shared working copy

  • erp5_bt_commit(bt_title, path_pattern='*supply_line*', dry_run=true) narrows the commit AND the export to matching paths; a scoped export writes only those files, so other people's uncommitted work is never swept or clobbered. skipped reports what was left out.
  • Huge BTs: summary_only=true / max_list=N cap the path lists (nothing is hidden silently — every list carries a count and a "more" marker).
  • Commit identites land as Klaus Wölfel automatically; push with plain git push.

Traps

  • An errored script call used to commit the work it had done before the exception — the error was caught inside the tool, so the request committed normally and left a half-applied fix. erp5_skin_call aborts its transaction on error since 2026-09-25 (error ⇒ nothing persisted), but keep writing mutation helpers idempotently (old/new marker pairs, replace-or-skip) and validate before mutating: patch order is arbitrary on this Python 2 instance (dict iteration is hash order), and halfway states may exist from older sessions.
  • Never trust a multi-part fix that "mostly succeeded": re-read all target objects afterwards — e.g. a scoped erp5_bt_status(path_pattern=...) for BT-tracked files, or erp5_read on each object.
  • Duplicate BT documents with one title (several installs): the tools resolve by highest id — a stale uninstalled copy can shadow the live one; check portal_templates when results look fossilised.
  • Template-wide exports DELETE any file in the BT directory that the BT does not export — never keep notes/READMEs inside a BT directory.
  • template_path_list patterns (e.g. web_page_module/GUIDE-*) match object ids, not references — a document whose id is auto-generated never enters the BT even though its reference matches. Create such objects with an explicit id (newContent(id=...)).
  • Editing objects via erp5_write replays every editable form field and can add default properties (e.g. Z SQL Method allow_simple_one_argument_traversal) — expect small export diffs; recreate an object from repo content when byte-exactness matters.
