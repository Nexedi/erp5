Add a MySQL catalog index for related lines (movement-table pattern)

Use this when listing by a related line is slow through the normal catalog, e.g. supply lines of products, transformation lines of a product. You index the lines into a dedicated MySQL table that mirrors the movement-table pattern of erp5_movement_table_catalog.

The 8 files (per index table, e.g. ProductSaleSupplyLines)

  • z0_drop_<x> (DROP TABLE IF EXISTS) and z_create_<x> (CREATE TABLE) — method ids registered under sql_clear_catalog so a cleared catalog recreates them.
  • z_catalog_<x>_list — registered under sql_catalog_object_list, filtered by portal type / condition; body is one DELETE + INSERT so a reindex updates rows in place without duplicates.
  • z0_uncatalog_<x> — registered under sql_uncatalog_object; single statement DELETE FROM <t> WHERE <dtml-sqltest uid op=eq type=int multiple>.
  • Each method also has a .catalog_keys.xml companion (filter / method registration).
  • Register all method ids in the BT property template_catalog_method_id_list.

Where the methods live (anatomy)

  • Z SQL Methods live inside the SQLCatalog, not on the tool: ZODB path portal_catalog/<sql_catalog_id>/<method_id> (e.g. portal_catalog/erp5_mysql_innodb/z_catalog_product_sale_supply_line_list), matching the BT export layout CatalogMethodTemplateItem/portal_catalog/erp5_mysql_innodb/….
  • portal_catalog._getOb(method_id) and restricted getattr(portal_catalog, method_id) return nothing — an inspection over the tool reports every method as MISSING and costs debugging detours. Restricted skin scripts cannot reach them; use trusted code (erp5_trusted_exec) or, better, erp5_catalog_method_read / erp5_catalog_method_write, which exist exactly for this.
  • List candidate ids: portal.portal_catalog.getSQLCatalog().objectIds() from a skin script, or the BT export files under CatalogMethodTemplateItem/.

Editing an existing method safely

  • Change src and arguments_src together through one manage_edit — that call re-parses the arguments into _arg and re-compiles the DTML template; editing only one of the two desynchronises the parsed state from the source the BT exports. erp5_catalog_method_write does exactly this (and refuses accidental connection_id changes unless force_connection=true). A failed write leaves the method untouched — re-read with erp5_catalog_method_read before retrying, and prefer full-source rewrites over pattern edits for multi-line changes.
  • arguments_src must list accessor names (getDestinationUid, getBasePrice...), never column names. Column names render as "instancemethod object has no attribute __getitem__" from DTML.
  • Date-range idiom for supply-line validity: the "Valid from" / "Valid until" fields are a paired range — getStartDateRangeMin / getStartDateRangeMax (cf. SupplyCell_asPredicate), not getStartDate/getStopDate. In arguments_src: those two names; in src: <dtml-sqlvar expr="getStartDateRangeMin[loop_item]" type="datetime" optional> / same for Max. optional keeps the column NULL when the line has no bound, and predicate logic must treat the NULL cases explicitly.
  • Values resolve per object via getattr, so rows are indexed per line; <dtml-sqlvar expr="getUid[loop_item]"> style loop variables come from the object-list loop.
  • Multi-statement separator inside one method: <dtml-var "'\0'"> (NUL character), like all ERP5 catalog methods.
  • Render optional values as or 0 (uid columns DEFAULT 0) and let dates stay NULL.
  • DDL conventions: uid BIGINT UNSIGNED NOT NULL PRIMARY KEY, party/product uid columns BIGINT UNSIGNED DEFAULT 0 with KEYs, ENGINE=InnoDB DEFAULT CHARSET=utf8mb4.
  • Filter expression like python: context.getPortalType() == 'Sale Supply Line' and context.getResourceValue() is not None and context.getResourceValue().getPortalType() == 'Product' — when it depends on more than portal_type, leave expression_cache_key EMPTY or it will silently never re-evaluate.

Migrating a live index (correcting an existing one)

  1. Patch the methods first: read with erp5_catalog_method_read, then write src and arguments_src together with erp5_catalog_method_write.
  2. Create/repair the table now: portal_catalog.upgradeSchema() (trusted code / a component; not from a skin script).
  3. Backfill: searchAndActivate(portal_type='Sale Supply Line', method_id='immediateReindexObject') — but this instance has no activity worker, so drain with erp5_activity_drain (use retry_stuck for stuck messages, cancel_stuck for poison ones). A plain immediateReindexObject loop also works in one call for a few hundred objects (329 ran synchronously in a single call during the supply-line session).
  4. Verify set-based (next section) and confirm the methods are not in drift: erp5_bt_status(path_pattern='*supply_line*').

Verify set-based, never row-by-row

  • Expected set: catalog query for the indexed lines (uids).
  • Actual set: SELECT GROUP_CONCAT(uid ORDER BY uid) FROM <table> via erp5_sql(format="rows") — compare as sets. A query may end in its own LIMIT (plain or OFFSET form): the tool only appends its own LIMIT when there is none, and date cells come back as ISO strings.
  • Orphans: LEFT JOIN catalog c ON t.uid=c.uid WHERE c.uid IS NULL must return 0.
  • Add a live test to woelfel_test (register the component id in template_test_id_list) and run it with erp5_live_test.

Getting it into the repository

Write the method sources as repo files and apply with erp5_bt_update_from_repository, or edit on the instance (erp5_catalog_method_write) and export with erp5_bt_export_to_repository — see GUIDE-BTSYNC-001. No scaffolding tool is needed: exporting the BT produces all 8 files. Trusted one-shot glue that a restricted skin script cannot run (upgradeSchema(), bulk reindex calls) goes through erp5_trusted_exec — no per-incident component + External Method bootstrap any more (see GUIDE-TRUSTED-001).
